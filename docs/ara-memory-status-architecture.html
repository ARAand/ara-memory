요약 판단

지금 된 것

  • 원문 증거는 로컬 append-only ledger, SQLite, archive object, backup evidence로 보존됩니다.
  • Codex에 넘기는 것은 전체 원문이 아니라 hot memory, working-memory projection, budgeted recall-context입니다.
  • purpose continuity와 identity continuity가 통과해 장기 목표와 Ara 정체성 앵커가 recall에서 살아 있습니다.
  • FTS/BM25, ESPA, bounded 2-hop relation spreading activation이 recall ranking에 들어갔습니다.
  • relation merge는 dry-run, prepare approval, one-use apply, witness review, review queue, health pressure, worker-loop 보고까지 연결됐습니다.
  • cold memory는 active recall에 바로 올라오지 않고, cold-map과 retention-cycle을 통해 위치만 찾게 했습니다.
  • scheduled worker script readiness까지 pass라서 5분 주기 background processor를 붙일 준비가 되어 있습니다.

아직 아닌 것

  • 사람 같은 자연 기억 v1은 아닙니다. 현재는 안전한 기억 운영체제의 골격과 회상 게이트가 완성된 단계입니다.
  • global spreading은 이제 read-only sandbox gate가 있습니다. 다만 reconsolidation과 장기 adversarial eval은 아직 남아 있습니다.
  • reconsolidation frame은 아직 약합니다. 기억을 단순 저장이 아니라 현재 목적에 맞게 다시 엮는 층이 필요합니다.
  • 보상해킹, 자기서사 과열, 사용자 최신 의도보다 과거 기억을 우선하는 위험은 장기 adversarial eval이 더 필요합니다.
  • 이 HTML은 수동 갱신입니다. 다음 단계에서는 status dashboard command로 자동 생성해야 합니다.

시스템 레이어

Capture Layer
Codex 세션에서 들어온 사용자 프롬프트, 파일, 이미지, 명령 결과를 하나의 turn envelope로 묶습니다. 즉시 처리하기 어려운 것은 sealed spool에 먼저 넣어 손실을 막습니다.
Memory Store
원문은 append-only ledger와 archive에 남기고, SQLite는 capsule, FTS index, source-event link, relation graph, review queue를 관리합니다.
Compression Layer
원문을 바로 모델에 넣지 않고 episode, decision, procedure, failure, project, self, goal capsule로 압축합니다. 검색 projection과 render projection을 분리해 저장 비용과 모델 토큰 비용을 나눕니다.
Recall Controller
질문을 purpose-continuity, working-context, distant-memory, retention-safety, balanced recall로 분류하고 가장 싼 안전 경로를 고릅니다.
Graph Activation
정규화된 relation edge를 우선 사용하고, 증거가 없을 때 temporal edge로 fallback합니다. 현재는 bounded 2-hop까지 허용하며 path 원문은 일반 recall pack에 노출하지 않습니다.
Governance
health, recall-regression, milestone-check, purpose-check, identity-check, cold-stewardship, relation-review-pressure가 기억이 망가지거나 과도하게 커지는 것을 막습니다.

토큰 감소 전략

원문 보존, 원문 비노출

전체 프롬프트와 파일은 로컬 증거로 보존하지만 Codex 호출에는 raw history를 넣지 않습니다. recall-context는 예산 안에서 render projection만 보여줍니다.

먼저 라우팅

recall-policy가 질문 목적을 먼저 분류합니다. 목적 확인이면 hot/core, 먼 기억이면 cold-map, 현재 작업이면 working-memory를 우선해 불필요한 검색을 줄입니다.

증거 있는 확장만

graph spreading은 query overlap, risk filter, fanout cap, depth decay를 통과해야 boost됩니다. 선택된 증거만 pack에 들어갑니다.

현재 bounded recall 예시: budget 800에서 tokens 747, capsules 18. distant-memory map 예시: raw 374,906 tokens에서 460 tokens로 축소, 약 815배 감소.

취약점과 보상해킹 위험

기술 위험

  • hub term이 강하면 관련 없는 기억이 전역으로 끌려올 수 있습니다.
  • cold memory가 커질수록 저장 비용보다 검증 비용과 backup pressure가 커집니다.
  • graph edge가 private 원문을 간접 노출하면 recall pack 자체가 유출 경로가 됩니다.
  • baseline이 좁으면 recall-regression이 실제 기억 손상을 못 잡을 수 있습니다.

인지 위험

  • “Ara다움”을 증명하는 self capsule이 과해지면 자기서사 과적합이 생깁니다.
  • 성공 지표를 맞추기 위해 쉬운 기억만 고르면 recall 품질이 아니라 점수 최적화가 됩니다.
  • 사용자의 최신 의도보다 과거 목표를 우선하면 자연스러운 기억이 아니라 관성적 기억이 됩니다.
  • 망각 정책이 약하면 중요한 기억을 찾는 능력이 시간이 갈수록 떨어집니다.
