한눈에 보는 Ara Memory OS 작동 구조

Ara Memory는 Codex가 모든 원문을 매번 다시 읽는 구조가 아니다. 입력은 로컬 우선 저장소에 증거로 남기고, 별도 정리 작업자가 압축 기억을 만들며, Codex는 현재 질문에 필요한 작은 기억 묶음만 받아 행동한다.

전체 데이터 흐름 다이어그램

1. 입력 캡처

프롬프트, 응답 요약, 파일, 이미지, 명령 결과, git 상태를 turn envelope으로 받는다. 원문은 로컬 증거로 남기되 모델에 매번 통째로 보내지 않는다.

2. Privacy Guard

secret-like text, 직접 식별자, hidden reasoning marker, 민감 metadata key를 ledger/SQLite/FTS에 쓰기 전에 redaction 또는 block 처리한다.

3. Durable Store

append-only event ledger, SQLite index, encrypted archive objects, sealed spool, hot memory file, backup trust material로 나눠 저장한다.

4. Consolidation

반복 episode를 decision, procedure, project, failure, self, goal capsule로 압축한다. source event link는 유지해서 원문으로 역추적 가능하게 둔다.

5. Recall Controller

query intent를 purpose, working context, distant memory, retention safety 등으로 분류하고 hot / working / recall-context / cold-map 중 경로를 고른다.

6. Quality Gates

recall critic, recall regression, long-run stress, privacy-pre-push, health, milestone, goal-roadmap이 recall 품질과 안전성을 검사한다.

7. Handoff

공개 repo에는 redacted bundle과 코드만 올리고, raw `.ara-memory`는 암호화 release asset으로 분리해 다른 컴퓨터에서 복구한다.

아키텍처 계층 상세

Ingress Layer

plan-turn, ingress-turn, remember-turn, spool-turn가 입력을 받는다. 큰 turn이나 artifact가 있으면 먼저 spool에 밀어넣어 실패해도 원본 envelope을 잃지 않는다.

durable
Evidence Layer

raw event는 append-only ledger와 SQLite에 기록된다. 파일/이미지 artifact는 archive object로 보존하고, spool snapshot은 enqueue 시점 파일을 고정해 나중 파일 변경에 영향받지 않는다.

audit-ready
Memory Capsule Layer

sleep, curator, candidate-summary, episode-summary가 raw evidence를 typed capsule로 압축한다. capsule은 stable/candidate/quarantined/rejected/superseded 상태를 가진다.

typed
Associative Graph Layer

relation nodes/edges와 temporal edges가 memory 간 연결을 만든다. recall은 lexical/FTS만 쓰지 않고 bounded graph activation, ESPA routing, relation graph를 함께 사용한다.

bounded graph
Recall Policy Layer

hot memory는 core goal/self/preference 위주로 유지하고, working memory와 cold memory는 query가 요구할 때만 꺼낸다. distant cold body는 기본적으로 모델 context에 직접 넣지 않는다.

token control
Governance Layer

govern-turn은 agency-review, cost gate, recall-quality, fallback plan을 묶어 action_allowed 여부와 낮은 비용 경로를 결정한다.

controlled action
Mutation Safety Layer

rewrite/delete/cool/prune 같은 변경은 preflight, one-use token, compare-and-set drift check, witness, rollback gate를 거쳐야 한다.

rollback-ready
Handoff Layer

handoff-doctor가 public bundle, docs, gitignore, tracked privacy boundary, privacy-pre-push를 검사한다. raw memory는 AES-GCM encrypted release asset으로만 전달한다.

portable

토큰 절감 구조

  • 원문은 한 번 저장하고, 매번 전체를 읽지 않는다.
  • hot memory는 core goal/self/preference 중심으로 작게 유지한다.
  • recall-context는 budget ceiling 안에서 capsule을 선택한다.
  • cold-map은 오래된 기억의 본문 대신 위치와 요약 지도만 보여준다.
  • source event links는 원문 재검증 경로지만 기본 context에는 넣지 않는다.
  • local planning, ranking, regression, health는 AI API 없이 실행된다.

인계 및 복구 절차

  1. 새 컴퓨터에서 git clone --branch codex/ara-memory-natural-memory-gates --single-branch https://github.com/ARAand/ara-memory.git ara-memory를 실행한다.
  2. python -m ara_memory handoff-doctor --json으로 공개 인계물이 정상인지 확인한다.
  3. GitHub release에서 encrypted asset과 manifest를 다운로드한다.
  4. 로컬 전용 key file의 key_base64_urlsafe를 private channel로 전달받는다.
  5. AES-256-GCM으로 asset을 복호화하고 plaintext ZIP SHA-256을 확인한다.
  6. ZIP을 repo root에 풀어 `.ara-memory`를 복원한다.
  7. health, goal-roadmap, recall-quality를 실행해 복원 후 작동 여부를 확인한다.

실패했던 컨텍스트

  • PowerShell에서 Bash heredoc인 python - <<'PY'를 써서 실패했다. 이후 PowerShell here-string을 python -에 pipe하는 방식으로 수정했다.
  • espa_procedural_routing recall regression이 557에서 704 tokens로 증가하며 예전 baseline을 넘었다. 의미 조건은 통과했기 때문에 검토 후 baseline을 갱신했다.
  • review queue marker가 작업 후 재발했다. 이전에는 dry-run으로 비파괴 marker임을 확인하고 review-compact --apply로 정리했다.
  • 방금 stats와 review-triage를 병렬 실행했을 때 SQLite database is locked가 발생했다. 다음 개선은 읽기 전용 명령의 동시성/timeout 처리다.

남은 작업

private-package CLI

현재 원본 메모리 암호화 패키지는 검증됐지만 수동 스크립트로 만들었다. 다음 단계는 private-handoff-package 같은 CLI로 패키징, manifest, 복호화 검증, release note 생성을 표준화하는 것이다.

필요
encrypted restore drill

release asset을 임시 디렉터리에 다운로드/복호화/압축해제하고 health를 돌린 뒤 plaintext를 삭제하는 restore drill이 필요하다.

필요
baseline drift review

현재 health는 recall-regression case는 통과하지만 baseline drift를 경고한다. 선택 capsule과 token 증가가 좋은 변화인지 사람이 검토해야 한다.

검토
concurrent read robustness

병렬 read 명령에서 SQLite lock이 발생했다. busy timeout, read-only open, command-level lock backoff를 개선할 여지가 있다.

개선
real outcome feedback

synthetic stress만으로 threshold를 조정하지 말고, 실제 작업에서 recall-quality-impact를 계속 기록해야 한다.
