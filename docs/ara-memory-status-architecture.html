Ara Memory OS 현재 작업 상황과 아키텍처

현재 시스템은 26시간 이상 제작 중인 장기 기억 저장소다. 목표는 모든 원문을 매번 읽는 구조가 아니라, 목적, 정체성, 결정, 실패, 작업 맥락, 망각 경계를 분리하고 필요한 맥락만 불러오는 자연스러운 기억 구조다. 이번 단계에서는 candidate-only 재통합 경로 위에 rollback witness와 review queue를 붙여, 더 강한 live memory 변형 전에 시스템 스스로 blocker를 볼 수 있게 만들었다.

완료된 축

  • 로컬 우선 저장소: SQLite, ledger, capsule, FTS, relation graph.
  • 상시 입력 경로: remember-turn, spool-turn, drain-spool.
  • 토큰 절감 recall: raw 전체 읽기 대신 capsule projection, recall-policy, working-memory pack.
  • 수명주기 분리: core, working, guarded, evidence, archive, reject.
  • 품질/안전 게이트: doctor, health, milestone, goal-roadmap, privacy-pre-push.
  • candidate-only 재통합: prepare, apply, review, strong shadow preflight.

이번 단계

  • SCHEMA_VERSION을 17로 올리고 reconsolidation_review_queue를 추가했다.
  • reconsolidation-review --record-queue가 fail/watch witness를 영속 큐로 기록한다.
  • fail 항목은 block-strong-reconsolidation으로 저장되어 강한 live 변형을 막는 신호가 된다.
  • witness가 다시 pass하면 같은 witness의 open queue가 resolved로 닫힌다.
  • health와 goal-roadmap이 open reconsolidation blocker pressure를 표시한다.
  • reconsolidation-review-queue 명령으로 open/resolved 큐를 조회할 수 있다.

현재 리스크

  • 강한 재통합은 아직 live capsule promote/supersede/rewrite/delete/cool 권한을 갖지 않는다.
  • rollback witness는 preview와 review queue까지 왔지만, 실제 live rollback 실행기는 아직 없다.
  • worker가 reconsolidation queue를 자동 기록하는 단계는 아직 붙지 않았다.
  • API 기반 AI memory worker는 아직 기본 경로가 아니다. 현재는 로컬 deterministic gate가 중심이다.
  • 보상해킹 방지는 시작됐지만, recall-policy feedback을 자동 정책 변경으로 연결하지 않는 제한이 유지되어야 한다.

아키텍처

1. Capture프롬프트, 파일, 이미지, 명령, 결정, 결과를 event 또는 turn envelope로 저장한다.
2. Guard비밀, 직접 식별자, hidden reasoning, 위험 텍스트를 저장 전 redaction 또는 차단한다.
3. Store원문 증거는 ledger/archive에 두고, 검색용 capsule과 graph는 SQLite/FTS로 분리한다.
4. Recall목적, 작업, distant memory, retention intent를 분류하고 작은 context pack만 렌더링한다.
5. Gateprepare/apply/review/queue/health가 강한 기억 변형 전 증거와 rollback 조건을 검증한다.

남은 작업과 예상 소요

worker 연동

정기 worker가 reconsolidation witness review를 재실행하고 --record-queue와 같은 큐 기록을 수행하게 한다.

2-3h
live rollback executor

rollback witness를 실제 복구 계획으로 바꾸되, shadow restore와 compare-and-set을 통과한 경우에만 live 실행한다.

5-8h
exception witness

증거 capsule 변경이 의도된 경우, 무조건 실패가 아니라 별도 승인된 예외 증거로 기록하는 경로를 만든다.

3-5h
AI memory worker

비용 한도 안에서 원문 전체를 비동기 분석하는 별도 memory AI를 둘지, Codex가 직접 큐만 호출할지 실험으로 결정한다.

6-10h
long-run stress test

대량 turn, 파일, 이미지 설명, 실패 로그를 넣고 토큰 감소율, recall 정확도, 큐 압력, 비용을 측정한다.

4-6h

다음 판단

  • 즉시 강한 live mutation을 열면 빠르지만 위험하다.
  • 다음 1순위는 worker가 blocker queue를 주기적으로 갱신하게 만드는 것이다.
  • 그 다음 rollback executor를 shadow-first로 구현해야 한다.
  • AI API 비용은 기본 경로가 아니라 optional batch summarizer로 제한하는 편이 낫다.
  • 이 기억의 목적은 더 많은 저장이 아니라, 원하는 맥락만 자연스럽게 떠오르게 하는 것이다.
